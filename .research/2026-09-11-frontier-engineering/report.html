Kiro Frontier Engineering은
현재 주장의 근거가 될까?

반복적인 사람 개입을 줄이자는 주장에는 강한 근거가 된다. 다만 사람이 방향과 결과를 판단하는 역할은 유지하며, 명세·작업 지침·AI 리뷰어도 권장하므로 AI-DLC 전체를 반대하는 글로 쓰기는 어렵다. [K2] [K5] [K7] [K8] [K10]

읽은 범위: 상위 안내 1개 + 하위 원칙 10개 전체, AWS 공식 글 2개, 현재 AI-DLC 저장소 문서 3개.
비교 대상: 9월 6일 「AWS AI-DLC에 대한 단상」의 현재 내용, 보조적으로 8월 31일 「Frontier Development의 다섯 습관」.
아래의 ‘지지·부분 지지·차이’는 자료를 대조한 해석이며, Kiro가 이 블로그 글이나 AI-DLC를 직접 평가한 결과가 아니다.
판정10개 원칙승인 위치 비교 현재 글의 주장별 검토직접 인용근거의 한계원문

근거로 쓰되, 무엇의 근거인지 좁혀야 한다

현재 글의 중심을 ‘사람이 반복해서 개입하던 일을 도구·검증·권한 설계로 줄여간다’로 잡으면 Kiro와 매우 가깝다. 원칙 2는 사람의 역할을 방향 설정과 결과 확인으로 좁혀가라고 하고, 원칙 8은 사람이 지켜보지 않아도 작동하는 권한 제한과 자동 검사를 요구한다. 원칙 10은 새 모델에서 예전 모델의 임시방편이 여전히 필요한지도 다시 보라고 한다. [K2] [K8] [K10]

반대로 ‘좋은 에이전틱 개발에는 사람의 검토·명세·리뷰어·작업 절차가 필요 없다’로 넓히면 이 자료와 맞지 않는다. Kiro는 사람이 의도와 완료 조건을 정하고 결과를 확인해야 한다고 하며, 방향을 정한 뒤 명세를 쓰고 AI 리뷰어와 작업 지침을 활용하도록 한다. 현재 글은 모든 사람이나 모든 절차를 당장 없애자는 글은 아니므로, 그 구분을 더 선명하게 쓰는 편이 좋다. [K1] [K3] [K5] [K7]

따라서 AI-DLC와의 가장 분명한 비교 지점은 ‘사람이 중요한가’가 아니라 ‘어떤 지점에서 사람의 응답을 계속 기다리게 하는가’다. 목표와 품질에 대한 사람의 책임은 공통이지만, Kiro는 실행 중 개입을 줄이고 위험한 행동에 승인을 좁혀가라고 하는 반면 AI-DLC는 선택된 단계가 끝날 때의 승인도 유지한다. [K2] [K7] [K8] [A2] [A4]

상위 페이지가 말하는 변화

상위 안내는 도구만 바꾸는 개발자와 일하는 방식을 바꾸는 개발자를 구분하며, 직접 코드를 작성하는 데서 에이전트가 코드를 만들 수 있는 환경을 준비하는 쪽으로 일이 이동한다고 설명한다. 그 환경을 만들려면 지침 작성, 코드 정리, 작업 범위 설정에 몇 주의 투자가 필요하고 초기에는 오히려 느릴 수 있다고 한다. [K0]

동시에 사람의 주의력과 판단이 계속 필요하다고 본다. 여러 에이전트 사이에서 맥락을 전환하고 품질을 유지해야 하며, 에이전트 결과를 가장 잘 검토하는 방법도 아직 정립되지 않았다고 인정한다. 이는 완성된 무인 개발 표준이나 생산성 비교 연구가 아니라, 현재 실무에서 권장하는 방향을 설명한 안내다. [K0]

하위 10개 원칙 전체

각 항목에서 Kiro가 실제로 말한 내용과, 현재 글 및 AI-DLC와 비교한 해석을 분리했다.

01공통 기반

코드 작성보다 의도와 완료 조건을 정한다

You are the architect, not the typist

원문 요약
개발자가 할 일은 요구사항과 제약, 완료 조건을 명확히 하고 결과가 그 의도에 맞는지 확인하는 쪽으로 이동한다. 권한별 접근 범위나 인증 만료 시 동작처럼 구체적인 조건을 주고, 코드는 에이전트가 작성하게 한다. [K1]
현재 글과 비교
사람이 목표와 검증 기준을 정하고 실행을 맡긴다는 주장과 맞는다. 다만 사람의 결과 확인까지 없애자는 내용은 아니며, 글에서 말하는 HITL 제거는 반복적인 실행 개입을 줄이는 뜻으로 한정해야 한다. [K1]
AI-DLC와 비교
AI가 계획하고 구현하되 사람이 중요한 결정을 내린다는 점에서 AI-DLC와도 가깝다. 이 원칙만으로 두 접근이 반대라고 주장하기는 어렵다. [K1] [A1]
02강한 지지

에이전트는 오래 일하게 하고 사람의 개입은 줄인다

Maximize agent time, minimize your involvement

원문 요약
사람이 매번 코드를 받고 직접 테스트해 오류를 전달하는 과정을 벗어나, 검증 방법까지 포함한 작업을 에이전트에게 맡긴다. 여러 에이전트를 병렬로 실행하고 결과는 나중에 검토하며, 경험과 도구가 쌓이면 수 시간이나 밤새 일하게 한다. [K2]
현재 글과 비교
반복 개입을 줄여 방향 설정과 결과 확인에 집중한다는 점에서 1절의 가장 직접적인 근거다. 긴 에이전트 실행 시간은 큰 제품을 한꺼번에 만든다는 뜻이 아니므로, 작은 기능 단위 작업과도 함께 적용할 수 있다. [K2]
AI-DLC와 비교
사람이 방향을 정한다는 점은 같지만, 승인 대기를 반복해서 줄이려는 목표는 단계별 승인을 유지하는 AI-DLC와 긴장 관계에 있다. 단계 안의 자율 실행과 단계 사이의 승인 대기는 구분해야 한다. [K2] [A2] [A4]
03지지하되 절차도 허용

에이전트가 이해하고 작업하기 좋은 코드베이스를 만든다

Build your codebase for agents

원문 요약
문서, 테스트, 모듈 구분, 타입, 빠른 빌드와 명확한 오류 메시지를 갖춘다. 큰 기존 시스템에서는 준비된 모듈부터 맡기고, 지침 파일·필요할 때 불러오는 작업 절차·환경 설정 스크립트·명령줄 도구·외부 시스템 연결 도구를 제공한다. 결정 이유도 다음 작업에서 읽을 수 있게 남긴다. [K3]
현재 글과 비교
좋은 도구와 실행 환경을 제공하고 사람이 머릿속으로 메우던 정보를 드러내자는 주장과 맞는다. 다만 절차를 담은 skill도 유용한 수단으로 인정하므로, 절차를 기록한 것 자체를 하네스 부채로 보면 원문과 어긋난다. [K3]
AI-DLC와 비교
요구사항·설계·결정을 저장소에 남기고 지침으로 작업을 돕는다는 점은 AI-DLC와 겹친다. 문서나 지침의 존재보다 실제로 어떤 행동을 제한하는지가 비교 대상이다. [K3] [A1] [A2]
04검증 주장에는 강한 지지

에이전트가 빠르게 검사하고 스스로 수정하게 한다

Give agents a fast feedback loop

원문 요약
사람이 보기 전에 에이전트가 로컬 테스트와 자동 검사, 화면 확인, 서비스 간 연동 테스트를 실행하고 실패를 수정할 수 있게 한다. 다양한 입력에서도 반드시 지켜야 할 조건을 확인하는 속성 기반 테스트도 권장한다. [K4]
현재 글과 비교
사람이 테스트 결과를 옮겨주거나 오류를 대신 해석하지 않도록 환경을 갖추자는 주장과 매우 가깝다. 하지만 여기서 빠른 피드백은 주로 코드가 맞게 동작하는지 알려주는 기술적 피드백이다. 실제 고객에게 작은 제품을 보여주고 요구사항을 바꾸는 과정까지 직접 입증하는 근거는 아니다. [K4]
AI-DLC와 비교
테스트와 품질 확인은 AI-DLC와 공통이다. 차이는 자동 검사가 사람의 반복 확인을 얼마나 대신하느냐에 있으며, AI-DLC가 테스트를 하지 않는다고 해석해서는 안 된다. [K4] [A1] [A4]
05부분 지지 · 해석 제한

구현보다 풀 문제와 오래 남을 설계 결정에 집중한다

Execution is cheap. Direction is everything.

원문 요약
문제 선택, 구조, 시스템 사이의 약속, 의존 관계처럼 바꾸기 어려운 결정에 시간을 쓴다. 두 설계가 모두 가능하면 에이전트에게 각각 시제품을 만들게 해 비교하고, 방향을 정한 뒤에는 코드 작성 전에 명확한 요구사항과 명세를 함께 작성하라고 한다. [K5]
현재 글과 비교
말로만 논쟁하지 말고 동작하는 결과를 만들어 비교하자는 점은 2절과 맞는다. 동시에 명세 기반 개발을 명시적으로 권장하므로, 만들기 전에 요구사항을 정리하는 일 자체가 잘못이라는 주장을 뒷받침하지는 않는다. [K5]
AI-DLC와 비교
사람이 방향과 설계를 판단하고, 요구사항을 명확히 한 다음 구현한다는 점에서 가깝다. 다만 이 페이지는 팀 전체가 모든 단계에서 승인하도록 요구하지 않는다. [K5] [A1] [A2]
06실험·검증 주장 지지

코드는 버릴 수 있어도 지켜야 할 동작은 남긴다

Treat code as disposable

원문 요약
잘못된 제품이면 이미 만든 코드에 매달리지 말고 버리거나 다시 만든다. 구현과 함께 없어질 수 있는 단위 테스트와 달리, 사용자가 기대하는 동작·항상 지켜야 할 조건·부하와 동시 처리 성능을 확인하는 테스트는 재작성 후에도 유지한다. [K6]
현재 글과 비교
작게 시도하고 결과를 보며 바꾸자는 태도와, 구현 대신 동작 조건을 검증하자는 생각을 지지한다. 다만 모든 작업을 vertical slice로 진행하라는 규정이나 항상 가장 작은 실험이 낫다는 비교 결과까지 담고 있지는 않다. [K6]
AI-DLC와 비교
품질과 요구사항을 지킨다는 일반 목표는 겹치지만, 읽은 AI-DLC 자료에서는 코드를 버리는 태도를 같은 비중의 원칙으로 내세우지 않는다. 직접 충돌한다고 판정할 근거도 없다. [K6] [A1] [A3]
07지지와 수정 필요가 함께 있음

품질 책임은 유지하며 리뷰와 운영 확인도 자동화한다

Hold AI output to human standards

원문 요약
처음에는 코드를 자세히 읽어 모델을 이해하되, 점차 AI 리뷰어가 여러 차례 피드백을 맡게 하고 사람은 설계·다른 시스템에 미치는 영향·보안 판단에 집중한다. 배포 이후에도 에이전트가 동작을 감시하고 문제가 생기면 수정하게 한다. [K7]
현재 글과 비교
리뷰 부담을 줄이고 제품 운영까지 책임져야 한다는 2·5절을 뒷받침한다. 반면 별도 AI 리뷰어를 명확히 권장하므로, Reviewer가 있다는 사실만으로 오래된 모델을 위한 불필요한 보조 장치라고 분류하면 맞지 않는다. [K7]
AI-DLC와 비교
사람이 품질에 책임지고 결과를 검토한다는 점은 같다. 다만 Kiro는 초기 리뷰를 AI에게 옮기고 사람의 주의를 선택적으로 쓰라고 하며, AI-DLC 문서는 단계별 승인도 유지한다. [K7] [A1] [A4]
08가장 강한 지지

감시 대신 권한 제한과 자동 검사로 자율 실행을 허용한다

Trust the boundaries, not the agent

원문 요약
파일·도구·네트워크·인증 정보 접근을 필요한 범위로 제한한 뒤 지속적인 감시 없이 실행하게 한다. 점차 허용 범위를 넓히되 되돌릴 수 없는 행동은 승인을 남기고, 운영 환경 접근 권한은 명시적으로 부여해야 한다. 보안 취약점과 비밀 유출 등을 자동으로 검사한다. [K8]
현재 글과 비교
허용 범위와 검증 방법을 제공해 사람이 대신할 일을 줄인다는 1·3절의 직접적인 근거다. 자율 실행을 강조하면서도 모든 승인을 없애지는 않는다는 점까지 함께 인용해야 한다. [K8]
AI-DLC와 비교
권한과 안전, 책임을 중요하게 본다는 점은 공통이지만 승인 위치가 다르다. Kiro는 되돌릴 수 없는 행동에 승인을 좁혀가라고 하고, AI-DLC는 선택된 단계의 완료 승인도 요구한다. [K8] [A2] [A4]
09양쪽과 넓게 일치

계획부터 운영까지 같은 원칙으로 에이전트를 활용한다

Use agents for everything, not just code

원문 요약
코드뿐 아니라 설계 문서, 장애 조사, 보고와 문서화에도 목표·정보·검증 방법·제한된 권한을 제공한다. 여러 에이전트가 같은 지침과 도구를 공유하게 하며, 다른 사람에게 공유할 결과는 검토하고 다듬는다. [K9]
현재 글과 비교
배포와 운영까지 에이전트의 역할을 넓힌다는 주장에 맞는다. 동시에 사람이 결과를 검토하는 역할은 유지하므로, 수작업을 줄이는 것과 책임을 없애는 것을 구분해야 한다. [K9]

이 자료로 결론 내릴 수 없는 것

이 페이지들은 Kiro가 권장하는 실무 방향을 보여주므로 ‘이런 접근을 공개적으로 권장한다’는 근거가 된다. 그러나 원칙별 효과를 대조군과 비교한 연구가 아니므로, 이 방식이 AI-DLC보다 몇 배 빠르거나 특정 하네스가 성능을 얼마나 떨어뜨리는지는 알 수 없다. 상위 안내 역시 아직 초기 단계이며 리뷰 방법 등이 정립되지 않았다고 말한다. [K0]

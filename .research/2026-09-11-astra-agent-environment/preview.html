Astra에 영상 제작을 맡겼더니 앱부터 만든 이야기

Giving agents the tools to finish the whole job

TL;DR

  • 모델의 능력을 끌어내려면 도구와 실행 환경이 뒷받침되어야 한다.
  • 앱의 기능을 MCP로 연결해 데모 영상 제작 전체를 맡길 수 있었다.
  • 모델의 속도와 비용만 달라져도 자동화할 일의 범위는 넓어질 것 같다.

시작하며

최근 astra로 블렌더에서 이것저것 만드는 사례들을 보면서, 모델의 공간 지각 능력이 많이 좋아졌다고 느꼈다.

개인적으로 최근 프론티어 모델, 즉 현재 가장 앞선 성능을 가진 모델들을 볼 때 관심을 두는 부분은 두 가지다. 얼마나 오래 하나의 문제를 붙잡고 해결할 수 있는지, 그리고 외부 도구와 환경을 얼마나 충분히 활용할 수 있는지다.

며칠씩 걸리는 작업을 맡기는 경험은 이미 하고 있었다. 그런데 블렌더 사례를 보니, 모델이 외부 프로그램을 활용해서 만들어내는 결과도 전보다 훨씬 복잡해졌다는 느낌이 들었다.

전에는 비전 모델, 즉 이미지와 화면을 이해하는 모델이 충분히 발전하면 사람이 쓰는 앱을 그대로 보고 조작하는 것으로 충분할 거라고 생각했다.

하지만 블렌더의 작업 과정을 살펴보고, 직접 영상 제작을 맡길 수 있는 앱까지 만들어보면서 생각이 조금 바뀌었다. 모델이 앱의 기능을 직접 사용할 수 있도록 환경을 만들어주는 것이 예상보다 훨씬 큰 차이를 만들었다.

1. 블렌더 사례에서 모델과 함께 봐야 할 것

OpenAI가 공개한 사례에서는 astra에 집과 가구, 정원을 만들어달라고 요청한다. 결과물은 블렌더에서 계속 수정할 수 있는 3D 장면이고, 같은 장면 안에서 카메라를 움직여 집을 둘러보는 영상도 만든다.1

흥미로웠던 부분은 중간 결과를 고치는 과정이었다. astra는 렌더링한 이미지, 즉 3D 장면을 이미지로 출력한 결과를 살펴보고 구도와 조명, 물체가 겹치는 부분을 수정했다. 사용자가 모든 물체의 위치와 수정 사항을 하나씩 지정하지 않아도 작업을 이어갔다.1

이때 astra는 Blender의 Python API를 사용했다. API는 다른 프로그램에서 기능을 호출할 수 있도록 열어둔 인터페이스다. 여기서는 코드를 통해 물체와 재질을 만들고, 조명과 카메라를 배치하는 식이다.1

카메라 촬영과 렌더링에는 블렌더를 백그라운드에서 실행하는 스크립트도 썼다. 화면을 직접 열어 살펴보는 작업과 API를 통한 작업을 함께 사용한 것이다.1

별도의 오픈소스 도구인 Blender MCP도 이런 접근을 돕는다. MCP(Model Context Protocol)는 에이전트가 외부 도구와 데이터를 사용할 수 있도록 연결하는 규약이다.2 Blender MCP는 장면 정보를 읽거나 물체와 재질을 수정하고, 블렌더 안에서 Python 코드를 실행하는 기능을 제공한다.3

Python API를 직접 쓰거나 MCP를 통해 연결하는 방식 모두 에이전트가 블렌더의 기능을 호출할 수 있게 해준다.

모델이 좋은 구도를 판단해도 그 구도로 카메라를 옮기고 다시 렌더링할 수 있어야 결과가 좋아진다. 블렌더 사례에서 눈에 들어온 것은 이 판단과 실행이 연결되어 있다는 점이었다.

2. 코드를 만드는 일보다 전달하는 일이 더 부담스러웠다

최근 회사에서 고객의 시스템 설계와 기술 도입을 돕는 SA(Solutions Architect)가 고객에게 코드를 전달할 수 있도록 하는 인증 과정을 도입하고 있었다.

마지막 프로젝트에서는 실제로 무언가를 빌드하고, 지정된 템플릿에 맞춰 데모 영상을 찍어서 제출해야 했다.

그런데 프론티어 모델을 쓰면서 겪는 변화와 이 인증이 강조하는 방향은 조금 어긋난다고 느꼈다. 최근 경험에서 요구사항과 작업 방법이 정해진 구현은 이미 에이전트에게 시간과 토큰을 들여 맡길 수 있는 일이었다. 고객도 직접 만들 수 있는 문제를 SA가 대신 구현해서 전달하는 데 얼마나 더 시간을 써야 할지 의문이 들었다.

정해진 기간에 결과물을 내려고 하면 고객의 요구사항을 필요 이상으로 단순화하고, 주변 업무의 맥락을 일부러 제외해서 그 안에 빌드할 수 있는 형태로 줄이게 되기 쉽다. 이렇게 줄인 결과물이 고객이 실제로 풀어야 하는 문제에서 멀어질 수 있다는 점이 마음에 걸렸다.

구현이 끝나도 전달할 준비가 남는다. 외부에 코드를 제공하기 위한 여러 보안 점검을 직접 수행하고, 고객이 코드를 이해하고 배포할 수 있도록 설명 문서와 발표자료도 만들어야 한다. 이 일을 모두 SA가 정해진 기간 안에 해야 한다.

내가 더 필요하다고 생각한 것은 고객이 자신의 요구사항과 업무 맥락을 가지고 직접 만들고 고칠 수 있게 돕는 일이었다. 구현을 에이전트에게 맡길 수 있게 됐다면, SA의 시간도 고객이 그 에이전트를 잘 쓸 수 있도록 요구사항과 도구, 실행 환경을 갖춰주는 데 더 쓰는 편이 낫다고 생각한다.

고객이 직접 만들더라도 배포할 코드의 보안과 품질은 확인해야 한다. 다만 처음부터 고객의 환경과 검토 절차 안에서 만들도록 도우면, 외부에서 만든 결과물을 넘기기 위해 별도로 준비하는 작업은 줄일 수 있을 것이다.

이런 생각을 하고 있으니, 대신 만든 결과물을 전달하기 위해 문서와 영상을 다시 손으로 준비하는 일이 더 부담스럽게 느껴졌다. 구현을 자동화한 뒤에도 설명과 전달에 필요한 반복 작업을 사람이 계속 맡아야 하는 셈이었다.

그래서 이번 영상 제작도 에이전트에게 전부 맡길 수 있으면 하고, 아니면 안 해야지 싶었다. 정해진 형식으로 촬영하고 자막과 설명을 붙이는 과정까지 함께 맡겨보고 싶었다.

3. Scribird와 PixelBankStudio를 거쳐 Storybird까지

촬영부터 자막, 음성 복제, 편집까지 여러 작업을 이어가야 했다. 이전에 같은 일을 5.6 sol에 맡겼을 때는 끝내 완수하지 못했다.

며칠 전 astra에 다시 맡겼더니 처음에는 비슷했다. 딱 봐도 이전처럼 잘 안될 것 같은 방법을 무던히 시도했다. 그런데 이번에는 필요한 기능을 갖춘 앱을 직접 만들어서 쓰는 게 어떻겠냐고 제안했다.

예전 같으면 앱을 만든다는 말부터 의심했을 것이다. 실제로 opus 4.8로 아이폰 앱을 만들었다가 원하는 대로 동작하지 않아, 앱을 만드는 쪽은 한동안 생각하지 않고 있었다.

다만 최근에는 경험이 조금 달라졌다. 5.6 sol이 약 3일 동안 스스로 작업해서 만든 Swift 앱이 Scribird였다.

그전에는 Python으로 만들어둔 PixelBankStudio를 Go로 옮기는 작업도 통째로 맡긴 적이 있었다. 에이전트가 약 5일 동안 스스로 진행해 마친 원샷 마이그레이션이었다.

Scribird를 만들고 PixelBankStudio를 옮기는 과정을 겪었으니, 이번에도 반신반의하면서 시켜볼 수 있었다. Scribird의 Swift 코드를 바탕으로 영상 제작에 필요한 기능을 정리해서 한꺼번에 요청했다. 내가 그 코드가 내부에서 어떻게 동작하는지 전부 이해하고 시작한 것도 아니었다.

그렇게 만든 앱이 Storybird다. astra가 약 3일 동안 작업해서 첫 버전이 나왔고, 원하는 형태로 쓰면서 다듬는 데 다시 3일 정도 걸렸다.

그 과정을 거친 뒤에는 요구사항 문서만 준비하면 내 목소리로 설명하는 데모 영상까지 만들 수 있는 작업 흐름을 갖추게 되었다.

4. 사람이 쓸 수 있는 앱을 에이전트도 끝까지 쓸 수 있게

Storybird를 만들 때 특별히 요청한 조건이 있었다.

사람이 화면에서 수동으로 사용할 수 있으면서, 에이전트도 필요한 기능을 전부 직접 호출할 수 있게 해달라는 것이었다. 중간에 사람이 버튼을 눌러줘야 다음 단계로 넘어가는 부분을 최대한 없애고 싶었다.

이를 위해 영상 제작에 필요한 기능 명세를 먼저 정리하고, 그 기능들을 MCP로 최대한 노출해달라고 요청했다. 앱의 기능을 에이전트가 찾아서 호출할 수 있게 만든다는 뜻이다.

요청한 구조를 단순화하면 아래와 같다. 사람이 쓰는 화면과 에이전트가 쓰는 MCP가 모두 Storybird의 기능으로 연결된다.

에이전트가 쓰는 제어 경로를 headless로 만든 셈이다. 여기서는 사람이 앱 화면을 조작하지 않아도 기능을 호출해 작업을 진행할 수 있다는 의미다. 촬영 대상의 화면이나 결과를 확인할 미리보기까지 없애는 것은 아니다.

영상 하나를 만들려면 각 단계가 연결되어야 한다. 촬영을 자동으로 해도 자막을 넣을 때 사람이 파일을 옮겨야 하거나, 음성을 만들고 나서 편집 앱에 직접 넣어줘야 한다면 그 지점에서 계속 사람을 기다리게 된다.

내가 원했던 것은 이 과정을 통째로 맡기는 것이었다. 그래서 사람에게 필요한 기능을 에이전트에게도 충분히 열어주는 것이 앱의 조건이었다.

예전에 PPT를 만들기 싫어서 MCP 도구를 만들 때도 비슷한 생각을 했었다.4 이번에는 촬영과 음성, 자막, 편집까지 연결하면서, 기능 하나를 자동화하는 것과 업무 전체를 맡기는 것의 차이를 더 크게 체감했다.

5. 더 좋은 모델이 일할 수 있는 환경

물론 이번 결과에는 astra의 능력이 좋아진 영향이 있었다고 생각한다. 이전에 끝내지 못했던 작업에서 필요한 도구를 제안하고, 앱을 만들고, 그 앱을 사용해 결과물을 완성하는 데까지 갔기 때문이다.

모델과 도구가 함께 바뀌었으니 각각의 기여를 수치로 나눌 수는 없다. 내가 직접 확인한 것은 더 나은 모델과 필요한 기능을 갖춘 앱을 함께 사용했을 때, 이전에 맡기지 못했던 작업 전체를 맡길 수 있었다는 점이다.

그 경험을 하고 나니, 화면을 잘 이해하는 능력과 기능을 직접 호출하는 경로를 함께 갖추는 쪽이 더 강력하다고 생각하게 되었다.

예를 들어 영상에 자막이 제대로 들어갔는지 판단할 때는 결과 화면을 보는 것이 도움이 된다. 반면 자막의 시작 시간을 정해진 값으로 바꾸는 일은 해당 기능을 직접 호출할 수 있으면 화면에서 조절할 필요가 줄어든다. 결과를 보고 판단하는 과정과 실제로 값을 바꾸는 과정에 각각 맞는 방법을 쓰는 것이다.

블렌더 사례에서도 API로 장면을 수정한 다음 렌더링 결과를 살펴봤다.1 화면을 보는 능력이 좋아질수록, 그 판단에 따라 장면을 정확하게 수정할 수 있는 도구도 더 유용해질 수 있다.

그래서 MCP를 붙였다는 사실만으로 충분하지는 않다. 업무를 끝내는 데 필요한 기능이 빠져 있다면 그 부분에서는 다시 사람에게 돌아와야 한다. 내가 요청했던 것도 MCP 연결 자체보다 영상 제작의 처음부터 끝까지 필요한 기능을 에이전트가 사용할 수 있게 해달라는 것이었다.

이전에 쓴 하네스 엔지니어링 글에서는 에이전트가 실행하고 결과를 확인하며 다시 시도할 수 있게 돕는 환경을 다뤘다.5 이번에는 그 환경에 들어갈 앱까지 에이전트가 만드는 경험을 한 셈이다.

6. 성능이 멈추고 속도와 비용만 달라져도

Storybird의 첫 버전이 약 3일 만에 나온 것을 보면서 다른 생각도 들었다.

몇 년 전이라면 돈을 받고 팔았을 법한 앱을, 내가 하기 싫은 업무 하나 때문에 만들고 있었다. 실제로 쓸 수 있게 다듬는 시간이 더 들었지만, 그 시간을 쓰고 나니 가장 귀찮고 복잡하던 일을 처음부터 끝까지 맡길 수 있었다.

지금은 이런 작업을 맡길 때 며칠을 기다릴 만한지, 모델 사용에 드는 토큰 비용을 감당할 만한지 따져보게 된다. 토큰은 모델이 읽고 생성하는 내용을 나누는 단위다.

자주 하는 일이라면 며칠을 투자할 만하지만, 한 번 하고 말 일이라면 그냥 손으로 하는 편이 낫다고 판단할 수도 있다.

그런데 현재 모델의 성능이 더 올라가지 않더라도, 응답 속도가 거의 실시간에 가까워지고 토큰 가격이 거의 0에 수렴하면 이 판단이 달라질 것 같다.

이번에는 영상 제작이 너무 귀찮아서 앱을 만들었다. 도구를 만드는 대기 시간과 비용이 훨씬 줄어든다면, 한 번 처리할 일에도 작은 도구를 만들어 쓰는 것이 자연스러워질 수 있다. 업무 방식이 바뀌면 그때 필요한 기능을 다시 고치면 된다.

모델이 빨라진다고 영상 렌더링이나 실제 촬영에 필요한 시간까지 없어지는 것은 아니다. 원하는 결과를 정하고 완성된 영상을 확인하는 일도 남는다. 다만 에이전트가 작업 방법을 찾고, 코드를 만들고, 실패한 부분을 고치는 동안의 대기와 비용이 줄어드는 것만으로도 맡겨볼 만한 일이 늘어날 것이다.

이전에는 만들 가치가 있는지 따져야 했던 도구를 필요할 때 만들어 쓸 수 있다면, 소프트웨어를 사용하는 방식도 달라질 것 같다. 이미 있는 앱에 업무를 맞추는 대신, 지금 해야 하는 업무에 맞는 기능을 더 쉽게 마련할 수 있기 때문이다.

마치며

한 번 맡겼다가 실패한 일을 다시 맡기는 데는 기대가 별로 없었다. 이번에도 전부 맡길 수 없으면 안 할 생각이었는데, 필요한 앱을 만들고 나니 그 일을 계속 맡길 수 있게 되었다.

그래서 에이전트가 어떤 일을 못 끝냈을 때, 모델이 더 좋아져야 할 문제인지 필요한 기능에 접근할 수 없어서 막힌 것인지 구분해볼 필요가 있다고 생각한다. 내가 겪은 영상 제작에서는 도구를 만드는 데까지 일을 맡겨볼 만했다.

그 도구를 준비하는 시간과 비용까지 줄어든다면, 지금은 귀찮아도 직접 처리하는 일들을 훨씬 쉽게 맡길 수 있을 것 같다. 더 높은 성능을 기다리지 않아도 바뀔 수 있는 일이 이미 꽤 많다는 생각이 든다.

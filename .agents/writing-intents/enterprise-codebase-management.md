# 소프트웨어 팩토리 시대의 엔터프라이즈 코드베이스 관리

여러 팀이 서비스를 독립적으로 개발하는 기업에서 코딩 에이전트가 필요한 기능을 어디서 발견하고 어느 버전의 정보를 믿고 구현할지 설명한다. 한국어 제목은 위와 같다. 출발점은 DDD에서 업무 모델의 경계와 그 사이의 관계를 명시하고, 마이크로서비스가 공개된 계약을 통해 느슨하게 결합되도록 설계하는 원칙이다. 호환되는 계약이 유지되는 한 제공 팀의 내부 변경이 소비 팀의 코드 수정·동시 배포로 번지지 않는다는 뜻이다. “Discover globally, understand locally”는 이 원칙을 저장소 검색과 버전이 고정된 로컬 구현에 적용한 표현으로, DDD의 원문 인용이나 저자가 새로 고안한 설계 원칙으로 제시하지 않는다. “Discover globally”의 검색 범위는 전사 모든 저장소의 코드와 문서 원문이다. 키워드나 식별자로 본문을 검색하고 결과에서 얻은 단서로 다시 찾는 도구 하나면 에이전트가 대부분의 개발 문제를 해결할 수 있으리라는 저자의 판단을 드러낸다. 이 검색은 전사 임베딩을 전제로 하지 않으며 서비스 카탈로그 조회보다 범위가 넓다. 참조하는 외부 저장소에서 제공하는 코드와 계약에 버전을 붙이고, 구현 시점에는 소비 저장소의 작업 환경에서 그 버전의 원문을 읽을 수 있게 한다. 이를 위해 전사 코드를 미리 임베딩해 두는 데는 효용이 없다는 입장이다.

Amazon에서 직접 경험한 팀 단위 모노레포와 서비스 간 별도 저장소를 도입에서 짧게 설명한다. 팀을 넘는 것과 저장소를 넘는 것은 다르며, 다른 팀 소유의 별도 원본에 의존하면 팀 저장소 하나를 수정하는 개발자도 멀티레포 의존성을 다룬다. 모노레포 자체는 별도 절에서 설명하지 않는다. 과거 이력 대신 에이전트 시대 기업들의 구체적인 현재 사례로 주장을 뒷받침한다. 도입에서는 Anthropic이 급증한 병합·체크아웃 부하로 모노레포를 Git에서 자체 버전 관리 시스템 Scion으로 옮긴 사실을 통해, 소프트웨어 팩토리에서는 코드 작성 속도가 버전 관리와 빌드 기반의 병목까지 바꾼다는 점을 보여준다. 이어서 여러 저장소에 걸친 개발에서 어느 버전을 공급할지로 논점을 옮긴다. Amazon의 사내 코드·비정형 문서 검색 MCP와 구현 경험, Cursor·Codex·Claude Code의 일반적인 로컬 탐색을 설명한다. Amazon에서 서비스 팀이 자기 코드와 공개 계약을 소유하고 독립적으로 배포하는 과정에서 제공하는 버전과 소비하는 버전이 저장소의 개발 방식에 자리잡았다는 저자의 경험을 중심에 둔다. 이 구조가 있으므로 검색으로 서비스를 발견하고 로컬의 해당 버전으로 구현할 수 있다. 이 사례를 MSA의 원칙 중 서비스별 소유권, 명시적인 인터페이스, 독립적인 배포를 코드와 계약 관리에 적용할 실무적 근거로 삼는다. DDD의 바운디드 컨텍스트와 경계를 넘는 정보의 교환 방식은 어떤 업무의 의미를 어느 서비스의 계약에서 찾을지 설명한다. 업무 프로세스는 추론에 맡기기 어려워 도메인별 유비쿼터스 언어로 온톨로지 등에 미리 정리하고 별도 의미 인덱스 없이 정확히 찾는 방식을 제안한다. AWS Labs가 실험적으로 소개한 CodeKB에 개인적으로 동의하지 않는다는 문장은 맺음말에 한 번만 둔다.

첨부 문서가 MSA의 API 설계를 에이전트의 지식 전달에 적용한 다섯 가지 원칙을 원래 의미와 순서로 설명한다. 각 바운디드 컨텍스트의 도메인 지식 소유, 각 저장소에서의 독립적인 이해·개발, 필요한 지식만 명시적인 인터페이스로 공개, 중앙에서 위치·소유권·관계 관리, 작업 시점에 필요한 버전의 원문 확보가 그 내용이다. 주문·결제 사례에 적용해 각 원칙이 개발자의 작업에 어떤 차이를 만드는지 보여준다.

업무 프로세스를 표현한 온톨로지가 맨 위, 설계 결정과 기능 계약을 담은 ADR이 가운데, 구현 코드와 테스트가 아래인 저자의 지식 계층을 한영 대응 도식으로 보여준다. 도메인 팀 저장소의 Turtle 파일로도 충분하고 공용 저장소에 두더라도 규칙과 변경 승인 권한은 해당 도메인 팀에 있다는 판단, 복잡한 프로세스를 C4 모델의 확대 방식처럼 업무 개요에서 상세 규칙까지 나눠 보는 방법, 저자가 직접 만든 ontology-writer와 adr-writer에서 이 구조가 어떻게 구현되는지를 선환불 예로 설명한다.

사내 코드 검색 조사에서 확인한 구조를 참고해, 공개 글에는 도입할 팀을 위한 OpenSearch 기반 추천 설계로 설명한다. 원문 역색인을 기본으로 두고 코드 자체의 임베딩은 이득이 확인될 때 선택적으로 쓴다. 함수의 호출 관계까지 분석한 설명을 임베딩하면 외부 동작을 보존하는 리팩터링도 LLM 재분석과 벡터 갱신을 일으킬 수 있다. 변경량이 큰 소프트웨어 팩토리에서 늘어나는 비용·시간과 오래된 분석을 읽을 가능성이 전사 기본 방식으로 권하지 않는 근거다. 제품 이름에 대한 의견은 맺음말의 한 문장에 둔다.

추천 설계는 한 개의 MCP 코드 검색 도구로 OpenSearch 키워드 검색과 코드 유사도 검색을 모두 제공한다. 호출·반환 예와 질의/색인 경로, push 기반 변경분 갱신과 주기적 원본 대조, 브랜치·커밋 범위, 권한 취소와 삭제, 대기열 분리와 최신성 지표를 블로그 독자가 구현 결정을 내릴 수 있을 만큼만 설명한다. 제안하는 인터페이스와 운영 주기는 사내 배포 명세나 실측치와 구분한다.

# 소프트웨어 팩토리 시대의 엔터프라이즈 코드베이스 관리

글 전체의 중심은 코드 면에서도 완결된 로컬 개발 환경이다. 작업 사본을 준비하거나 의존 버전을 변경할 때 소비 저장소의 선언에 따라 필요한 외부 구현 소스·패키지·클라이언트·계약을 미리 동기화한다. 루틴한 개발 중 외부 저장소에서 매번 코드를 읽거나 가져오는 구조를 피하고, 동기화 이후에는 로컬에서 구현·빌드·테스트가 가능해야 한다. 한국어 제목은 위와 같다. 출발점은 DDD에서 업무 모델의 경계와 그 사이의 관계를 명시하고, 마이크로서비스가 공개된 계약을 통해 느슨하게 결합되도록 설계하는 원칙이다. 호환되는 계약이 유지되는 한 제공 팀의 내부 변경이 소비 팀의 코드 수정·동시 배포로 번지지 않는다는 뜻이다. “Discover globally, understand locally”는 이 원칙을 저장소 검색과 버전이 고정된 로컬 구현에 적용한 표현으로, DDD의 원문 인용이나 저자가 새로 고안한 설계 원칙으로 제시하지 않는다. “Discover globally”의 검색 범위는 전사 모든 저장소의 코드와 문서 원문이다. 키워드나 식별자로 본문을 검색하고 결과에서 얻은 단서로 다시 찾는 도구 하나면 에이전트가 대부분의 개발 문제를 해결할 수 있으리라는 저자의 판단을 드러낸다. 이 검색은 전사 임베딩을 전제로 하지 않으며 서비스 카탈로그 조회보다 범위가 넓다. 참조하는 외부 저장소에서 제공하는 코드와 계약에 버전을 붙이고, 구현 시점에는 소비 저장소의 작업 환경에서 그 버전의 원문을 읽을 수 있게 한다. 키워드 검색을 기본으로 삼고, 식별자를 모르는 경우에는 함수 본문의 유사도 검색으로 후보를 찾을 수 있게 한다.

Amazon에서 직접 경험한 팀 단위 모노레포와 서비스 간 별도 저장소를 도입에서 짧게 설명한다. 팀을 넘는 것과 저장소를 넘는 것은 다르며, 다른 팀 소유의 별도 원본에 의존하면 팀 저장소 하나를 수정하는 개발자도 멀티레포 의존성을 다룬다. 모노레포 자체는 별도 절에서 설명하지 않는다. 과거 이력 대신 에이전트 시대 기업들의 구체적인 현재 사례로 주장을 뒷받침한다. 도입에서는 Anthropic이 급증한 병합·체크아웃 부하로 모노레포를 Git에서 자체 버전 관리 시스템 Scion으로 옮긴 사실을 통해, 소프트웨어 팩토리에서는 코드 작성 속도가 버전 관리와 빌드 기반의 병목까지 바꾼다는 점을 보여준다. 이어서 여러 저장소에 걸친 개발에서 어느 버전을 공급할지로 논점을 옮긴다. Amazon의 사내 코드·비정형 문서 검색 MCP와 구현 경험, Cursor의 로컬 검색과 Claude Code·Codex의 grep 중심 탐색 설계를 설명한다. Claude Code 팀이 밝힌 검색 인터페이스 선택과 OpenAI의 Codex 프롬프팅 가이드를 각각 인용한다. grep 실행 성능 향상이나 양사 모델의 grep 전용 훈련으로 확대하지 않는다. Amazon에서 서비스 팀이 자기 코드와 공개 계약을 소유하고 독립적으로 배포하는 과정에서 제공하는 버전과 소비하는 버전이 저장소의 개발 방식에 자리잡았다는 저자의 경험을 중심에 둔다. 이 구조가 있으므로 검색으로 서비스를 발견하고 로컬의 해당 버전으로 구현할 수 있다. 이 사례를 MSA의 원칙 중 서비스별 소유권, 명시적인 인터페이스, 독립적인 배포를 코드와 계약 관리에 적용할 실무적 근거로 삼는다. DDD의 바운디드 컨텍스트와 경계를 넘는 정보의 교환 방식은 어떤 업무의 의미를 어느 서비스의 계약에서 찾을지 설명한다. 업무 프로세스는 추론에 맡기기 어려워 도메인별 유비쿼터스 언어로 온톨로지 등에 미리 정리하고 별도 의미 인덱스 없이 정확히 찾는 방식을 제안한다.

첨부 문서가 MSA의 API 설계를 에이전트의 지식 전달에 적용한 다섯 가지 원칙을 원래 의미와 순서로 설명한다. 각 바운디드 컨텍스트의 도메인 지식 소유, 각 저장소에서의 독립적인 이해·개발, 필요한 지식만 명시적인 인터페이스로 공개, 중앙에서 위치·소유권·관계 관리, 작업 시점에 필요한 버전의 원문 확보가 그 내용이다. 주문·결제 사례에 적용해 각 원칙이 개발자의 작업에 어떤 차이를 만드는지 보여준다.

업무 프로세스를 표현한 온톨로지가 맨 위, 설계 결정과 기능 계약을 담은 ADR이 가운데, 구현 코드와 테스트가 아래인 저자의 지식 계층을 한영 대응 도식으로 보여준다. 도메인 팀 저장소의 Turtle 파일로도 충분하고 공용 저장소에 두더라도 규칙과 변경 승인 권한은 해당 도메인 팀에 있다는 판단, 복잡한 프로세스를 C4 모델의 확대 방식처럼 업무 개요에서 상세 규칙까지 나눠 보는 방법, 저자가 직접 만든 ontology-writer와 adr-writer에서 이 구조가 어떻게 구현되는지를 선환불 예로 설명한다.

사내 코드 검색 조사에서 확인한 구조를 참고해, 공개 글에는 도입할 팀을 위한 OpenSearch 기반 추천 설계로 설명한다. 원문 역색인을 기본으로 두고 코드 자체의 임베딩은 이득이 확인될 때 선택적으로 쓴다. 개별 대안 제품의 평가나 구현 비교는 글에서 제외한다.

추천 설계는 한 개의 MCP 코드 검색 도구로 OpenSearch 키워드 검색과 코드 유사도 검색을 모두 제공한다. 호출·반환 예와 질의/색인 경로, push 기반 변경분 갱신과 주기적 원본 대조, 브랜치·커밋 범위, 권한 취소와 삭제, 대기열 분리와 최신성 지표를 블로그 독자가 구현 결정을 내릴 수 있을 만큼만 설명한다. 제안하는 인터페이스와 운영 주기는 사내 배포 명세나 실측치와 구분한다.

색인은 조건부 외부 검색을 지원하는 구현 선택이다. 글은 색인의 필요성보다 평시의 코드 공급과 예외적 외부 검색을 어떻게 분리하는지에 초점을 둔다. 전사 검색에 텍스트 색인을 두는 이유는 GitHub의 2023년 코드 검색 베타 사례로 설명한다. 메모리에 캐시된 파일에서 얻은 ripgrep 실측과 115TB 전체를 훑는 비용 추산을 구분한다. Blackbird의 n-gram 색인은 GitHub 사례이고 OpenSearch는 저자의 사내 구현 제안이다.

BC의 완결성은 자신의 코드·규약·채택한 외부 계약·테스트만으로 일상 변경을 설명하고 검증할 수 있다는 설계 목표다. 생산자의 실시간 구현 열람은 일상 작업의 전제가 아니다. 최초 연동·계약 버전 변경은 소유 팀의 공개 명세로, 관행과 베스트 프랙티스는 참고 사례로, 계약과 관측이 어긋난 장애는 실제 실행 리비전의 구현으로 확인한다. 검색 빈도에 대한 팀의 기대와 개발자 조사에서 관측한 사용 목적은 구분한다. 에이전트의 로컬 우선 경로, 외부 조회 목적·자료 권위·정확한 리비전과 실패 응답을 한영 글의 구조도·예시와 공개 MCP 도구 명세에 함께 반영한다.

Cursor의 정규식 검색 글은 대형 작업 저장소에서 에이전트가 반복 검색할 때의 대기 시간, 로컬 텍스트 색인으로 후보를 좁힌 뒤 원문을 확인하는 원리, 기준 커밋에 작업 중인 변경을 반영하는 이유를 설명하는 데 사용한다. Cursor가 검색용 코드베이스 임베딩을 중단하고 필요할 때 로컬 파일을 검색하는 방식을 택했다는 팀 설명과 현행 문서를 먼저 제시한다. Instant Grep의 로컬 텍스트 색인은 그 탐색을 빠르게 하는 내부 구현으로 이어서 설명한다.

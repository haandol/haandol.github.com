# 엔터프라이즈 AX 글의 의도

대상 원고: [한국어](../../_posts/2026-11-05-enterprise-wide-ax-essentials.md) · [영어](../../_en/2026-11-05-enterprise-wide-ax-essentials.md)

## 독자와 질문

엔터프라이즈 AX를 추진하는 업무·도메인 전문가와 개발자가 독자다. FDE가 초기 구축을 마친 뒤에도 업무 전문가가 자신의 언어로 변경을 요청하고 결과를 검증하며 시스템을 발전시키려면 무엇을 갖춰야 하는지 설명한다.

## 전체 글의 중심 주장

엔터프라이즈 AX는 공통 지식, 프로세스 분석, 요구사항 정리, 업무 자동화, 소프트웨어 개발의 각 단계에 필요한 솔루션을 갖추고 연결해 구축해야 한다. 전문가가 업무 기준과 성공 여부를 판단하면, 연결된 솔루션들이 분석·구현·검증·개선을 이어받아야 한다. 이 구조가 FDE의 초기 구축 이후에도 개발자의 지속적인 수동 관리 없이 업무 변경과 운영 개선을 가능하게 해야 한다.

업무의 의미와 규칙은 모델에서 코드까지 유지되어야 한다. DDD의 핵심 철학과 구현 디테일로부터 도메인 로직을 보호하는 설계 원칙은 이 목표를 뒷받침하는 아이디어다. 글의 중심은 특정 방법론의 전면 도입이 아니라 단계별 솔루션을 통한 비즈니스 자율 운영이다.

## 단계별 솔루션의 역할

| 단계 | 담당 솔루션과 역할 |
| --- | --- |
| 공통 지식 | 컨텍스트 레이어 솔루션이 문서 검색·RAG, 그래프, 온톨로지를 제공한다. 업무·코딩 에이전트는 MCP·도구로 접근하고 검증된 변경을 반영한다. |
| 프로세스 분석 | 현재·목표 프로세스와 영향 범위, 자동화할 부분을 정리한다. |
| 요구사항 정리 | 업무 규칙·예외를 구현 계약과 검증 사례로 관리한다. |
| 업무 자동화 | 에이전트·도구를 구성하고 실행·관찰·검증·흐름 개선을 맡는다. |
| 소프트웨어 개발 | Software Factory가 필요한 코드·도구를 구현·연결·검증하고 후속 변경을 수행한다. |

공통 지식은 모든 단계의 공유 기반이며 전체 AX를 대신하는 단일 솔루션이 아니다. 각 단계의 기능과 단계 사이의 전달이 함께 갖춰져야 한다. FDE는 초기 모델·솔루션·연결을 구축하고, 이후 전문가는 업무 판단과 결과 검증을 주도한다.

## 구성과 표현 기준

- 단계별 구성 요소는 본문·표·그림에서 일관되게 ‘솔루션’으로 부른다. 공통 지식은 ‘컨텍스트 레이어 솔루션’, 영어로는 ‘Context Layer Solution’으로 표기한다. 실제 구현 요소를 설명할 때는 API·애플리케이션 등 해당 대상을 구체적으로 쓴다.

- 시작하며는 다섯 단계와 단계별 솔루션 연결이라는 전체 주장을 제시한다. 특정 솔루션 소개 문단으로 초점을 옮기지 않는다. 개별 솔루션의 세부 역할과 연결은 해당 본문에서 설명한다.
- 1절은 비즈니스 프로세스가 개발자의 기술적 해석·설계·계층을 거쳐 코드가 되는 과정을 설명한다. 팀의 업무 이해도·숙련도·용어·프로그래밍 언어·구현 환경 때문에 업무 의미가 누락되거나 변형될 수 있다는 문제에서, DDD의 공통 업무 언어와 공유 모델, 그 의미가 통하는 범위인 바운디드 컨텍스트로 이어간다. DDD는 설계 아이디어의 출처로 쓰며, 방법론 도입 여부를 해명하는 문장은 본문에 넣지 않는다.
- 솔루션 구조를 설명하는 그림에는 솔루션과 담당 역할을 보인다. 의존성은 양파형 구조로, 컨텍스트 레이어 솔루션의 검색 기능과 MCP 연결은 솔루션 경계로 설명한다. 잉크버드의 이름·링크·3D 화면은 공통 지식의 전체 프로세스 조망 예시로 둔다.
- 기술 설명 글로 쓴다. 불필요한 개인 작업 이력·진행 상태·방어적 사족을 뺀다. 기업 설명은 AWS·팔란티어 FDE의 솔루션 기반 접근에 집중한다. 한·영의 주장과 그림은 대응시키고 기존 글 URL을 유지한다.

이 기준은 수정 전 사용자에게 전체 의도를 설명하고 편집 범위를 판단할 때 사용한다. 원고에 그대로 붙이는 소개문이나 작성 이력으로 사용하지 않는다.

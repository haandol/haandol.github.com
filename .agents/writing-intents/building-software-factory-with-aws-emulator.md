# Software Factory 구축 런북의 의도

## 독자와 질문

AI 코딩 에이전트를 사용하고 있으며 제품의 개발·개선을 자동화하려는 개발자와 기술 리더가 독자다. Software Factory의 정의를 반복하기보다, 어떤 준비와 실행 절차를 거쳐 구축하고 자동화 범위를 넓힐지 구체적으로 답한다.

## 전체 글의 중심 주장

처음에는 사람이 문제와 성공 조건을 정하고 에이전트가 구현·검증하는 L2 수준으로 제품을 만들어 PMF를 찾는다. 제품의 유용성과 반복 수요를 확인한 뒤, 반복되는 작업의 실행·검증·문제 발견·배포·개발 방식 개선을 단계적으로 자동화한다. 자율화 수준을 높이려면 루프 밖에서 사람이 준비하고 운영해야 하는 평가 기준, 실행 환경, 권한, 복구와 책임 체계도 늘어나므로 처음부터 완전 자동화를 구축하는 것은 좋은 투자 순서가 아니다. 실제 사람의 총노동 시간이 반드시 단조롭게 늘어난다는 주장으로 바꾸지 않는다.

## 사례와 논지의 역할

자동화의 비용은 사람이 개발 루프 밖에서 루프 자체의 실패 양상(failure mode)을 찾아내고 수정하는 일로 구체화한다. 에이전트 루프는 입출력만으로 내부 실행 경로를 이해하기 어려워 사실상 블랙박스처럼 보이므로, 단계별 입력·도구 호출·상태·평가 결과를 연결하는 정교한 observability가 필요하다. 관측 체계를 구성하고, 실패를 재현·분석하며, 실행·검증 절차를 고쳐 다시 확인하는 데 드는 시간과 노력을 초기 과잉 자동화를 피해야 하는 이유로 설명한다. 이 논지는 단계적 구축이라는 전체 주장을 뒷받침하며 관측 도구 소개로 글의 주제를 바꾸지 않는다.

- AWS Emulator를 중심 사례로 삼는다. 작은 시제품에서 시작해 실제 AWS로 확인한 테스트, 문제 발견, 이슈 수정, 병합 검사와 릴리스로 이어진 공개 구조를 구체적으로 설명한다. 공개된 사실과 독자에게 제안하는 구축 절차를 구분한다.
- OpenAI의 Codex 기반 내부 제품·Harness Engineering·Symphony와 Anthropic의 Claude Code 팀 사례는 자동화 확대 과정에서 무엇에 투자했는지를 비교한다. 각 도구의 기능을 그 회사 제품 전체의 운영 방식으로 일반화하거나 회사의 자율성 순위를 단정하지 않는다.
- L1~L5는 글에서 쓰는 비공식 구분이다. 제품 개선 루프, 프로덕션 배포 자동화, AI 개발 시스템 자체의 재귀적 개선을 구분한다. 하네스 개선은 후자에 필요한 제한된 실천이며 그것만으로 엄밀한 L5를 달성했다고 주장하지 않는다.
- 이전 Software Factory 글의 평가·KPI·텐션 메트릭 논의를 짧게 이어받아 실행 절차로 발전시킨다. 이전 엔터프라이즈 AX 글의 솔루션 기반 접근과 연결해 공통 실행·검증·복구 기반과 업무별 기준을 분리하고, 개인의 수동 운용 없이 재사용 가능한 솔루션으로 제공하는 방법을 설명한다.
- 마치며에는 저자가 직접 제공한 운영 경험을 담는다. 잉크버드와 픽셀뱅크는 L3를 기본으로 일부 L4 흐름을 운영한다. CloudWatch 알람을 받으면 AgentCore Runtime을 통해 하나의 Codex 세션에서 장애 분석·코드 수정·리뷰·PR 생성을 처리하고, 간단하거나 긴급한 버그는 바로 배포한다. 기본 Lambda 호출의 15분 제한 때문에 장기 작업을 나누고 상태를 이어야 하는 부담과, 현재 서비스 규모에서는 한 세션으로 충분하다는 선택을 설명한다. 이 경험을 현재 제품과 반복 업무에 맞춰 자동화를 넓힌다는 전체 주장에 연결한다. 제공되지 않은 승인·검증 정책이나 성과 수치를 지어내지 않는다.

## 형식과 범위

런북 성격의 기술 블로그 글로 쓴다. 단계별 입력·할 일·산출물·다음 단계 조건과 실패 시 대응이 드러나게 한다. 자연스러운 짧은 문단과 구체적인 작업 예시를 사용한다. 출처가 없는 개인 경험, 성과, 회사 내부 절차를 만들어내지 않는다. 한국어 원고와 완전한 영어 대응본을 작성·검토한다. 사용자가 두 원고의 게시를 요청했으므로 검토 후 발행에 필요한 커밋·푸시와 게시 확인까지 수행한다.

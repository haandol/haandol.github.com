# 코딩 에이전트와 소프트웨어 팩토리가 바꾼 개발 방식

코딩 에이전트를 사용하는 개발자와 제품 책임자가 독자다. 이전 글과 RFTCR을 모르는 독자도 에이전트가 계획까지 세우면 어떤 요구사항을 맡기고 어떤 결과를 확인해야 하는지 이해하도록, 선행 글 없이 읽을 수 있는 독립적인 글로 쓴다. 원래 모델에서 이어갈 통찰은 요구사항·기능·작업·코드 사이에서 책임과 근거를 어디에 둘지 분명히 하는 것이다.

‘시작하며’는 저자가 2025년에 코딩 에이전트로 소프트웨어를 개발하는 베스트 프랙티스를 찾다가 그 과정을 RFTCR로 정리한 경험에서 출발한다. 리팩터링을 떠올려 순서를 기억하기 쉽게 붙인 이름이라는 배경을 짧게 설명한다. 이전 글을 쓴 뒤 에이전트가 빠르게 발전해, 사람이 직접 하던 계획·작업 추적·재계획의 대부분을 맡게 됐음을 설명한다. 코드 생성 도중 사람이 개입할 단계가 줄었고, 사람이 인계용 Task 목록을 따로 유지할 필요는 없어졌다. 이러한 변화와 소프트웨어 팩토리에서 출시 이후의 관찰도 다시 기획과 개발로 이어지는 SDLC의 변화를 보여준 뒤에 RLO(Requirement → Loop → Outcome)를 처음 소개한다.

‘마치며’는 짧은 한 문단으로 맺는다. 기획, 개발·검증, 출시 후 운영과 성과 측정을 연결해야 하므로 조직에서는 그 흐름을 공통 솔루션으로 묶고, 업무 규칙과 지표는 조직별로 정하는 편이 좋다는 저자의 의견을 담는다.

요구사항은 해결할 사용자 문제, 원하는 변화와 제약을 담는다. AX의 업무 자동화와 개발 자동화를 같은 업무 의미로 연결하고, ALPS의 PRD에서 ADR로 구현 계약을 인계하는 역할을 보여준다. Discovery는 해결책을 시험하고, Delivery는 합의한 동작을 구현·검증하며, Learning은 반복되는 실패의 근거로 기획·개발 방법을 개선한다. 제품이 현장에서 어떤 결과를 냈는지가 다음 작업의 근거다.

잉크버드와 픽셀뱅크의 장애 대응, 저자가 직접 해 본 종이 목업과 가상의 학원용 주간 리포트 실험을 구분한다. 한·영 제목은 코딩 에이전트와 소프트웨어 팩토리가 가져온 개발 방식의 변화를 명사구나 평서문으로 표현한다. 두 언어의 글은 같은 논지와 사례를 전달한다.
